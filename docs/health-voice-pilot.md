# Голосовой диалог Health: пилот

Кнопка «Поговорить» в существующем Health-кабинете открывает диалог:
микрофон → `/api/transcribe` → существующий `sendBodyAiMessage` →
`/api/session` (action: `healthSpeech`) → воспроизведение. История и контекст чата остаются общими.
Озвучивание использует существующий слот функции: лимит 12 функций Hobby не превышается.
Диалог до первичной анкеты, Realtime, перебивание голосом и база литературы
в этот этап не входят. Клинические промпты и кризисные маршруты не менялись.

## Включение в Preview

- `VITE_HEALTH_VOICE_ENABLED=true` — кнопка, требуется пересборка.
- `HEALTH_VOICE_ENABLED=true` — серверное озвучивание и подписи ответов.
- `HEALTH_TTS_MODEL` — необязательно; по умолчанию `gpt-4o-mini-tts`.
- Нужны существующие `OPENAI_API_KEY`, `CLIENT_API_SIGNING_SECRET`,
  настройки Supabase и разрешённого origin. Новых секретов и миграций нет.
- По умолчанию оба флага выключены. Отключение серверного флага блокирует
  озвучивание сразу; для скрытия кнопки выключить клиентский флаг и пересобрать.

## Устройства и приватность

Запись доступна по HTTPS (или localhost). Проверка микрофона занимает 5 секунд
и не отправляет звук на сервер. Индикатор подтверждает сигнал, а не качество
распознавания. Пользователь отдельно разрешает отправку голосовых сообщений.
Выбор динамика показывается только при поддержке `setSinkId`; иначе устройство
выбирают в системе. Пробный ответ и кнопка «Да, слышу» проверяют слышимость:
браузер сам не может подтвердить физический звук.

По умолчанию запись завершается кнопкой «Я закончил» или через 45 секунд.
Основная кнопка меняется: «Говорите» → «Я закончил» → «Остановить».
Проверки устройств необязательны и находятся в свёрнутых настройках звука.
Без сигнала запись прекращается через 12 секунд. Автопродолжение выключено;
его можно включить в настройках (автоотправка после паузы 1,2 секунды).
Ответы с safety_note или низкой уверенностью не запускают следующую запись.
Пауза, закрытие, скрытие вкладки и смена устройства останавливают микрофон.
Уже отправленное сообщение может завершиться и сохраниться в истории после паузы,
но не должно автоматически прозвучать или запустить новый захват.
При ошибке речи остаётся текстовый ввод; ответ ИИ сохраняется даже при сбое TTS.

TTS требует клиентский токен Health и доступ к сессии. Произвольный текст не
озвучивается: ответ подписан сервером на 10 минут и привязан к сессии и тексту.
Применяется существующее маскирование контактов; бинарные ответы имеют no-store.
Не сохранять реальные аудио/медицинские данные в тестовые фикстуры и логи.

## Стоимость и ограничения

STT и чат используют существующие механизмы учёта сервиса. TTS пока не списывается
с кошелька пользователя: расходы несёт сервис. Есть лимит 120 частей за 10 минут
на существующем rate-limit механизме, но это не бюджетный потолок. Перед широким
запуском нужны согласованные тарифы, лимиты расходов провайдера и мониторинг.

## Ускорение и восстановление

Полный подписанный ответ делится без потери текста на первую часть до 240 символов
и следующие до 420. Сервер проверяет подпись всего ответа и сам выбирает часть
по индексу. Во время воспроизведения загружается одна следующая часть.
Серверный таймаут каждой части — 20 секунд, клиентский — 25 секунд вместе с телом
ответа. Повтор озвучивания не отправляет повторно вопрос и не генерирует новый
ответ (подпись действительна 10 минут). При остановке отменяются все загрузки.
В логах TTS только этап, HTTP-статус, длина и длительность — без текста и токенов.
В голосовом чате добавлена инструкция отвечать коротко без сокращения важных
предупреждений; модель и медицинские ограничения сохранены.

## Следующий этап: Realtime/WebRTC

Для устранения последовательного ожидания STT → текст → TTS нужен постоянный
WebRTC-канал с прямым speech-to-speech. Сервер авторизует сессию и задаёт правила,
контекст и инструменты; браузер передаёт и принимает аудиотреки. Постоянный ключ
провайдера остаётся на сервере. Нужны серверный контроль сессии, сохранение обеих
сторон диалога, прерывание ответа, лимит длительности/расходов и клинические тесты.
Это проект следующей версии, здесь Realtime ещё не подключён. Целевую задержку
следует замерять на реальных устройствах, включая p50/p95, а не обещать заранее.
Документация: https://developers.openai.com/api/docs/guides/voice-webrtc
и https://developers.openai.com/api/docs/guides/voice-server-controls

## Автоматические проверки

```bash
npm run test:health-speech
npm run test:voice-audio-mime
npm run e2e:health-voice
VITE_HEALTH_VOICE_ENABLED=true npm run build
```

E2E поднимает Vite самостоятельно и требует установленный Chromium Playwright
(`npx playwright install chromium`) либо `CHROMIUM_PATH`. Можно передать
`TEST_BASE_URL` уже запущенного Vite с включённым флагом. API, микрофон и
воспроизведение в тесте подменены; это не проверка реального OpenAI или слышимости.

## Обязательная ручная приёмка перед Production

На Preview с тестовой сессией проверить Chrome Android, Safari iPhone и desktop:
разрешение/отказ микрофона, реальное распознавание русского текста, слышимость,
Bluetooth, системный выбор выхода, блокировку автозвука, несколько реплик подряд,
паузу/закрытие/смену вкладки во время каждого этапа, сетевой сбой, истёкший доступ,
историю после перезагрузки, переход к специалисту, текстовый fallback и существующие
кризисные сценарии. Отдельно проверить стоимость, задержку и отключение флагами.
Реальные API и физические устройства локальными мок-тестами не проверены.
