# Партнёрская программа — основа v1

Статус: реализованы тестовый транзакционный учёт, защищённый API и раздел кабинета. Изменения проверяются локально; миграция на рабочей базе и публикация ещё не выполнены.

## Условия

- Базовая доля специалиста — 25% от стоимости использования сервиса прикреплённым пациентом. Это доля выручки, а не прибыли после расходов на ИИ.
- Support и Health (в коде `body`) используют одинаковые правила. В каждом модуле у пациента один получатель партнёрской доли в данный момент.
- Начисление возникает при подтверждённом списании за сервис. Пополнение, резерв, неуспешный запрос и личная консультация специалиста не входят в базу.
- Тестовые 22 000 единиц дают при полном расходовании 5 500 тестовых единиц специалисту. Они не подлежат выплате и не конвертируются в деньги после запуска платежей.
- Бонусные единицы не дают денежного вознаграждения. Оплаченные единицы учитываются отдельно от тестовых и бонусных.
- Для оплаченного пакета сохраняются количество единиц и фактически уплаченная цена после скидки в копейках. Курс не предполагается равным 1 рублю за единицу.
- Пример: пакет 22 000 единиц за 1 000 рублей; расход 2 200 единиц соответствует 100 рублям базы, начисление — 25 рублей. Пример не задаёт тариф.
- Комиссии эквайринга и расходы сервиса не вычитаются из базы в этой версии. Налоговые и договорные условия, срок удержания и порядок выплат необходимо определить перед денежным запуском.
- Ставка хранится в версии условий; её изменение действует только на новые списания. По умолчанию 2500 базисных пунктов.
- При смене специалиста старые начисления остаются прежнему получателю; новые идут новому. Задним числом начисления не создаются.
- Прикрепление и коммерческая доля не дают автоматического доступа к медицинским данным. Пациенту показывается участие специалиста в программе. Клинические рекомендации и длина диалога не зависят от вознаграждения.

## Реализованный контракт расчёта

`lib/partners/accounting.js` — независимое ядро без доступа к базе и платежам.
`allocatedRevenueKopecks` распределяет цену пакета накопительно, без потери копеек на мелких списаниях.
`calculatePartnerAccrual` считает разницу накопленных начислений, включая отрицательную корректировку при возврате.
`selectPartnerAttachment` выбирает историческое прикрепление в рамках пациента, модуля и пилота и отклоняет пересечения.
Деньги всегда остаются ожидающими: ядро не разрешает выплату.

Проверка: `node scripts/test-partner-accounting.js`.

## Денежный этап: оставшаяся архитектура

Существующие точки: `lib/usage/wallet.js`, RPC `consume_usage_credits`, журнал `usage_ledger`.
Не добавлять независимую запись начисления после RPC: сбой между операциями потеряет начисление.

1. Ввести историю партнёрского прикрепления с owner, expert, module, pilot, началом и концом действия; использовать подтверждённую сервером связь пациента со специалистом. Для общего контура нужен явный идентификатор пилота.
2. Ввести партии средств (`test`, `bonus`, `paid`) и распределение каждого списания по партиям. Порядок расходования: тестовые, бонусные, оплаченные; внутри категории FIFO. У оплаченной партии — подтверждённый платёж, исходные единицы и цена в копейках.
3. В одной транзакции блокировать кошелёк, списывать партии, сохранять usage_ledger и партнёрскую запись. Уникальный ключ исходное списание + партия защищает от повторных начислений. Повтор с отличающимися параметрами отклонять.
4. Запись начисления содержит ссылку на списание, партию и снимок прикрепления/ставки, module, pilot, базу, единицу измерения, сумму и статус. Накопительный счётчик ведётся отдельно для получателя, версии ставки и источника средств. Доступ только через сервер с проверкой полномочий; RLS и запрет клиентской записи.
5. Возврат ссылается на исходную запись и создаёт обратную проводку исходному получателю по исходной ставке. Повторный/избыточный возврат запрещён. Возврат неиспользованного остатка пакета не отменяет комиссию за уже оказанную услугу. После выплаты корректировка создаёт долг к зачёту, не удаляет историю.
6. Отдельные состояния: тестовое; ожидает подтверждения; доступно к выплате; выплачено; сторнировано. Платёжная интеграция должна подтвердить оплату и завершение срока удержания; тестовые записи никогда не переходят в денежные.
7. Кабинет специалиста: ставка, число прикреплённых пациентов, расход за период, тестовые начисления, ожидающие рубли, доступно к выплате, выплачено, журнал. Доступ к чужому пилоту/специалисту запрещён.
8. Перед включением: транзакционные тесты повторов и параллельных списаний, смешанных партий, частичных возвратов, смены специалиста/ставки, изоляции пилотов, модулей и прав кабинета.

## Что реализовано для тестового запуска

- Миграция `20261027062352_partner_test_accruals.sql`: AFTER INSERT trigger на `usage_ledger`. Списание и начисление коммитятся или откатываются вместе. Исторические операции не пересчитываются.
- Источник — активное `patient_assignments.primary_expert_id`; совместный доступ `patient_access` не даёт второй комиссии. Для Support поддержаны оба формата связи: canonical owner и legacy public_code. Неактивные специалисты исключены.
- Снимок получателя и организации, отдельный счёт по кошельку, прикреплению, специалисту, модулю и пилоту. Ставка тестового запуска фиксирована 25%. Дроби накапливаются до целой единицы.
- Только разрешённые AI-операции; консультации, резервы, пополнения и произвольные корректировки не создают комиссию. `partner_funding_kind` у текущих кошельков — `test`; `paid` и `bonus` исключены. Смешанные денежные партии пока не реализованы.
- В Support пилот сверяется с канонической сессией, организация — с её организацией. В Health сейчас поддерживается общий контур `main`; получатель выбирается только при единственном активном прикреплении среди организаций. Неоднозначные связи не дают начислений до исправления. Пропущенные начисления автоматически задним числом не восстанавливаются.
- `refund_partner_test_usage` доступна только серверной роли: ссылка на исходное списание, ограничение суммы, защита повторов, атомарное восстановление кошелька и обратное начисление прежнему специалисту. Для вызова использовать новый глобально уникальный request ID на операцию. Это серверная функция, кнопка возврата не добавлялась.
- `getPartnerProgram` использует проверенную сессию специалиста, его права на организацию и модуль, серверный pilot_id. ID специалиста/пилота из браузера игнорируются. Таблицы и RPC закрыты для anon/authenticated; RLS включена, SECURITY DEFINER не используется.
- Кабинет показывает итоги за всё время, количество пациентов с ненулевыми начислениями и 50 последних операций. Обновление вручную; при смене контекста старые ответы отбрасываются. Отсутствующая миграция показывается как недоступность программы, а не нулевой баланс.
- Применение миграции включает только новые тестовые начисления, включая списания оставшихся старых тестовых балансов. Откат приложения не удаляет проводки. Для остановки тестового учёта администратор БД может отключить `accrue_partner_test_usage`; накопленные данные сохраняются. Не удалять таблицы с проводками.

## Проверки и выпуск

Команды: `npm run test:partner-accounting`, `npm run test:partner-database`, `npm run test:partner-api`, `npm run test:partner-browser`, `npm run build`.
Для браузерного теста: `npx playwright install chromium`.
Тест базы использует изолированный PostgreSQL/PGlite, таблицы из baseline и RPC из `026-usage-credits.sql`; данные полностью синтетические. Проверяются права, повторы, округление, смена врача, возвраты и откат. PGlite использует одно соединение: многосоединительная конкуренция на удалённой базе этим тестом не проверена.
Браузерный тест использует mock API для проверки загрузки, мобильного экрана, смены модуля и ошибок; это не проверка опубликованного сервиса.

Порядок выпуска: проверить миграцию на тестовой копии актуальной схемы, применить её, опубликовать приложение, затем выполнить реальное тестовое списание и сверить кабинет. Денежные выплаты остаются выключенными. До публикации Production не изменён.
