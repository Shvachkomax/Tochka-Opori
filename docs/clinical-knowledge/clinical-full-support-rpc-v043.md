# Clinical Longitudinal v0.4.3 — исходные Support RPC на полной тестовой схеме

## Где проводились проверки
- **Tochka-Opori-Preview-Test** — уже существующая отдельная тестовая база PostgreSQL 17.6 с реальными таблицами и исходными функциями C1/C2. Её идентификаторы не нужны для работы интерфейса.
- Медицинская production-БД **не использовалась**.
- Клинический архив временно создавался **внутри транзакции** только на время теста. Использовались полностью искусственные пациенты, врачи, препарат и назначение; тест закончился `ROLLBACK`.
- Никаких постоянных медицинских таблиц, разрешений или лекарственных записей в Preview-Test не создано.

## Файлы и результат
1. `scripts/test-clinical-c2-medication.sql` из `main` успешно отработал на Preview-Test без изменений. Оригинальный C2 проверяет назначения, изменения, отзыв, роли, повторные команды, невозможность UPDATE/DELETE, валидацию графиков и клинические события. После его запуска осталось 0 учебных назначений, авторизаций и концептов.
2. `scripts/065-clinical-medication-archive-staging-ONLY.sql` — отдельный opt-in скрипт создания неизменяемого медархива и трёх функций-обёрток, выполняющих оригинальные `public.activate_medication_order`, `public.supersede_medication_order`, `public.revoke_medication_order` с атомарным клиническим снимком.
3. `scripts/068-clinical-full-c2-rpc-archive-preview-test.sql` — **реальные** исходные C2 RPC (не имитации) вызваны через новые обёртки в одной PostgreSQL-транзакции. Тест прошёл и доказал: три архивные записи (активация, замена, отзыв), два этапа новой дозировки, корректное медицинское авторство, одновременный откат базового назначения при сбое архива, отказ замены старого назначения без архивной версии и отсутствие доступа у `anon`/обычного клиента к новому архиву.
4. `lib/clinical/medication-archive-route.js` — отдельная чистая функция безопасного выбора RPC. `api/specialist.js` использует её только после существующей авторизации специалиста; флаг `CLINICAL_MEDICATION_ARCHIVE_ENABLED` по умолчанию выключен. **Без fallback:** сбой включённого архива не может автоматически вызвать старый неархивируемый RPC.
5. `scripts/test-clinical-medication-rpc-routing.js` — регрессия для трёх включаемых и выключаемых RPC, запрета неподдерживаемых имён. Проверки функции прошли.

## Границы утверждений
- Проверена **транзакционная SQL-цепочка настоящих RPC** в PostgreSQL Preview-Test.
- **Не проверен** полный HTTP-вход через Vercel с настоящим сеансом специалиста, cookie/CORS, согласиями, повторными вкладками, мобильным браузером и просмотром клинических версий.
- Медицинские данные клинических пациентов не копировали и не выгружали. Стенд Preview-Test расположен вне Российской Федерации — в него не следует вводить реальные истории пациентов.
- Не выполнены двухпроцессный нагрузочный тест, восстановление после рестарта PostgreSQL и юридическая проверка обработки медицинских данных.
- Исходные назначения C2 уже имеют неизменяемые версии; новый медархив добавляет независимую цепочку **проверенных событий жизненного цикла**, а не заменяет медицинский механизм назначения.
- Для существующих курсов лечения необходима согласованная миграция исходных версий в архив. Пока попытка архивировать `supersede` без v1 **отклоняется**, а не создаёт ложную полную историю.
- Поле `verified_authorization_checked` означает валидную запись в реестре разрешений, **не** подлинную электронную подпись врача. Проверка личности на уровне HTTP ещё впереди.

## Что делаем перед тестированием врачом
1. Подготовить отдельный защищённый Vercel Preview, привязанный исключительно к медицинскому тестовому проекту, без production API-ключей.
2. После бэкапа и проверки секрета подключения применить `065` **только** к отдельному medical staging, протестировать разрешения `service_role`.
3. Наполнить staging синтетическими пользователями и назначениями, проверить HTTP-сессию врача, ограничения организаций, CSRF/Origin и права при смене врача.
4. Включить на этой площадке флаг `CLINICAL_MEDICATION_ARCHIVE_ENABLED=true` и доступ к хронологии только для проверенных тестовых врачей. Должна быть готова система просмотра версий без утечки пациентских ID или клинических данных других организаций.
5. Выполнить браузерный E2E: авторизоваться, открыть искусственного пациента, создать назначение, изменить его, отменить, увидеть все версии; проверить отказ постороннему врачу.
6. Только после прохождения этих пунктов пригласить владельца проекта на врачебное тестирование. `main` и production не менять без отдельного разрешения.

## Текущее решение
**SQL-этап v0.4.3 пройден.** Подготовка защищённого браузерного Preview и прав доступа — следующий этап. Ни архив, ни серверный флаг в production пока не включены.
