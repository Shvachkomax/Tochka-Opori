# Единые правила баз и публикаций

Решение владельца от 04.11.2026: одна основная база для основного сайта и рабочих сайтов партнёров; одна постоянная тестовая база для экспериментальных веток. Дополнительные базы требуют отдельного согласования.

## Правила подключения

- Серверные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` всегда относятся к одной базе; менять их согласованно.
- `DEPLOYMENT_PURPOSE=live` разрешён только рабочим публикациям. `test` — тестовому проекту. `demo` запрещает установку URL и серверного ключа.
- Рабочая база общая; права пациента, специалиста и организации сохраняются. Для партнёра обязателен серверный `DEPLOYMENT_ORGANIZATION_ID` соответствующей организации рабочей базы.
- Общая база не означает общий доступ ко всем пациентам. Проверки межорганизационных границ обязательны перед публикацией партнёрского сайта.
- Preview, E2E и синтетические данные используют только постоянную тестовую базу. Тестовые идентификаторы организаций нельзя переносить в рабочую конфигурацию.
- Исключения отдельных веток проверяются отдельно: они имеют приоритет над общими переменными Preview.
- Ключи, реальные записи и выгрузки окружения не сохраняются в Git. Ключи остаются серверными Secrets.
- Изменение переменных Vercel действует на новые сборки. Старые Preview и опубликованные сайты не меняют подключение автоматически.
- Отключение новых Preview не отзывает старые ссылки и не удаляет установленные в них ключи. Старые Preview с рабочими подключениями требуется отдельно вывести из обращения.
- Переключение URL не переносит исторические данные. Миграция записей, если нужна, выполняется отдельно с проверкой связей и прав.

## Проверка перед публикацией

`npm run check:database-architecture` проверяет назначение, URL, наличие серверного ключа и соответствие ref/role для legacy JWT без сетевых запросов. Для непрозрачных ключей принадлежность подтверждает Supabase при подключении. Скрипт не проверяет подпись JWT, действительность ключа или права организаций.

`npm run test:database-architecture` выполняет изолированные проверки синтетических конфигураций. Проверка включена в `npm run build`; настройки Vercel не должны обходить эту команду.

Перед выпуском проверить точные проект, ветку, SHA и окружение, пройти авторизованные синтетические тесты на тестовой базе и убедиться в отсутствии межорганизационного доступа. Production smoke проводится без чтения пациентских записей.

## Текущее состояние внедрения

Настройки рабочих подключений и маршрута новых Preview обновлены в Vercel. Это не является завершённым rollout: нужны новые проверенные публикации, отдельная проверка серверных ключей тестового проекта, проверка изоляции АнМед и вывод старых Preview с рабочими подключениями. Изменения этого документа и проверки сборки ещё не опубликованы.
